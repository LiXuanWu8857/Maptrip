# 共享找客熱點 — 設計草稿（未實作，先討論定案）

> 目標：讓司機除了「自己的」找客熱區，還能看到**別的司機**的熱點。
> 分兩階段：**Phase 1 群組/車隊**（現在就有用、隱私單純）→ **Phase 2 全體去識別化池**（隨用戶變多才發威）。
> 兩階段**核心相同**（去識別化網格＋時段），只差「池子是一個隊、還是全體」。
> **這份是草稿**：資料模型／Firestore 規則／UI 流程／隱私防線／風險，定案後才動程式。

---

## 0. 先講現實（科學一點）
熱點要「夠多人的上車點」才準。**目前實際使用者≈1 人**，所以「全體熱點」短期內幾乎等於你自己的資料。
→ 這也是「先做群組」的原因：**幾個認識的司機朋友一起用，馬上就有感**；全體池子要養、要等人。

---

## 1. 共用的核心：去識別化網格

不管群組還全體，池子裡**只存「格子的次數」**，絕不存座標、身分、時間點、車資。

- **格子 `cellId`**：把上車點吸到粗網格（建議 **300m**）＋當時「時段桶」＋「平日/假日」。
  - `gLat = round(lat/CELL)*CELL`、`gLng = round(lng/CELL)*CELL`（CELL≈0.003°≈330m）
  - `dayType` ∈ {`wk` 平日, `we` 假日/週末}（沿用 hotspots.js 的 `isOffDay`）
  - `bucket` ∈ 0–7（沿用 hotspots.js 的 8 段時段 `_bucketOf`）
  - **格子文件欄位**：`{ gLat, gLng, dayType, bucket, count, updatedAt }`（**沒有 uid、沒有精確座標、沒有車資**）
- **k-匿名**：讀取時**只顯示 `count ≥ N` 的格子**（Phase 1 群組 N=2、Phase 2 全體 N=5～10），避免洩漏某人的私房點、也濾雜訊。

> 用「分欄位（gLat/gLng/dayType/bucket）」而不是把它們塞進 doc id，是為了能用 Firestore 複合查詢
> 拉「當前時段＋附近緯度帶」的格子，再在前端過濾經度（見 §4）。

---

## 2. 資料模型（Firestore，不需後端）

### Phase 1：群組/車隊
```
groups/{groupId}                     { name, ownerUid, createdAt, memberCount }
groups/{groupId}/members/{uid}       { name, joinedAt }
groups/{groupId}/grid/{cellId}       { gLat, gLng, dayType, bucket, count, updatedAt }
groupInvites/{CODE}                  { groupId, by, createdAt }      // 沿用現有邀請碼機制的做法
users/{uid}/meta/prefs               { shareHotspots: bool, groupId: string|null }
```
- 一個司機**加入一個隊**（`prefs.groupId`）；`shareHotspots` 決定「要不要貢獻＋看」。
- 加入方式**比照現有記帳者邀請碼**（`createInvite/redeemInvite/processInviteClaims` 的同型流程）。

### Phase 2：全體去識別化池
```
hotspotGrid/{cellId}                 { gLat, gLng, dayType, bucket, count, updatedAt }
users/{uid}/meta/prefs.shareGlobal   bool
```
- **格子結構與 Phase 1 完全相同**，只是集合路徑從 `groups/{gid}/grid` 換成 `hotspotGrid`。
- → **前端 90% 程式共用**，只差「貢獻/讀取指向哪個集合」。

## 3. 貢獻流程（寫入）

- **時機**：每完成一趟「載客」（有上車點 coords[0]、非「其他」）且 `shareHotspots` 開 → 對該格子 `count +1`。
  ```js
  ref.doc(cellId).set({ gLat, gLng, dayType, bucket,
                        count: firebase.firestore.FieldValue.increment(1),
                        updatedAt: Date.now() }, { merge: true });
  ```
- **一趟只加一次**（前端去重，避免重試/重畫重複灌）。
- **舊資料回填**：首次開啟共享時，可**一次性**把歷史上車點貢獻進去（分批、限流，避免爆量寫入）。v1 可先不做、只從「開啟後的新趟」開始累積（最單純）。
- **去識別化**：寫進去的只有 `cellId`（粗格）＋`count`＋時段類別。**沒有你是誰、實際幾點、去哪、多少錢。**

---

## 4. 讀取流程（查詢＋排名）

1. 取當下位置 → 算 `dayType`＋`bucket`＋你所在格子。
2. 查「當前時段＋附近緯度帶」的格子（複合查詢，需建索引）：
   ```
   where(dayType==dt).where(bucket==b).where(gLat >= latMin).where(gLat <= latMax)
   ```
   回來後前端再過濾 `gLng` 在範圍內（例如中心 ±2km）。
3. **k-匿名過濾**：丟掉 `count < N` 的格子。
4. 排名：`count` 為主，可加「近期加權」（`updatedAt` 越新略加權，反映需求變化）。
5. 地名：沿用現有 Nominatim reverse + `maptrip_geocache`（只對前幾名反查，省額度）。

**成本**：一次開啟約查回附近數十個格子（Firestore 免費額度 5 萬讀/日，綽綽有餘）。

## 5. UI 流程（接進現有「找客熱區」面板）

- 面板頂端加**來源切換**：`我的` ／ `隊` ／ `全體`（依有沒有加入隊、有沒有開全體顯示）。
- **開關**（`meta/prefs`）：
  - 「加入共享熱點」＝**貢獻我的去識別化上車點 ＋ 看得到大家的**（對等、預設關、可退出）。
  - 群組：`建立車隊` / `輸入邀請碼加入車隊`（比照記帳者邀請碼三步驟卡）。
- 面板文案要說清楚：**只分享「去識別化的上車熱度」，不會分享你的行程、車資或身分。**

## 6. 安全與防濫用（Firestore 規則＝安全根，你部署）

### 隱私
- 格子文件無 uid、無精確座標、無車資、無實際時間點 → 就算整張網格外洩，也只是「哪裡需求高」的**聚合熱度**，查不到個人。
- k-匿名（count 門檻）確保單一司機的私房點不會被看見。

### 寫入權限
- **群組**：只有「該隊成員」且 `shareHotspots==true` 能寫該隊 grid。規則用 `get(members/{uid})` 驗成員。
- **全體**：登入者可寫 `hotspotGrid`（Beta 心態）。
- **限制每次只能 +1**：規則檢查 `request.resource.data.count == (resource.data.count) + 1`（建立時需 `== 1`），
  擋一次灌很多。**注意：規則無法原生「限制每人每分鐘幾次」**——per-trip 前端去重＋+1 規則能擋大宗濫用，
  殘餘「有人慢慢刷」的風險**接受為 Beta**（動機低、要刷歪一座城市成本極高）。

### 讀取權限
- 群組 grid：僅成員可讀。全體 grid：登入者可讀（本來就是要給大家看）。

## 7. 可重用的既有東西（省工、降風險）
- **網格/時段/假日判斷**：`hotspots.js` 的 `_bucketOf`、`isOffDay/_isOffDay`、聚類邏輯 → 抽成共用純函式（`_cellId`、`_dayType`）。
- **邀請碼/加入**：記帳者那套 `createInvite/redeemInvite/processInviteClaims` 的同型流程，改成「加入車隊」。
- **找客熱區面板**：`hotspots.js` 現有面板加「來源切換」，不必重寫。
- **地名快取**：`finance.js`/`hotspots.js` 已有 Nominatim + `maptrip_geocache`。

## 8. 分階段落地

**Phase 1（群組/車隊）— 先做、能驗證**
1. `meta/prefs`（shareHotspots/groupId）＋ 開關 UI。
2. 建隊/加入（邀請碼）＋ `groups/*`、`members/*`。
3. 完成趟時貢獻 `groups/{gid}/grid`（+1，前端去重）。
4. 面板「隊」來源：查詢＋k-匿名＋排名。
5. Firestore 規則（成員才可讀寫該隊 grid、+1 限制）＋ 第二帳號實測。
6. 純函式測試（`_cellId`/`_dayType`/排名/k-匿名過濾）＋ 瀏覽器接線測試。

**Phase 2（全體池）— 之後開**
- 同一套程式，路徑換 `hotspotGrid`；加「貢獻/查看全體」開關；k-匿名門檻調高（5–10）。
- 觀察：貢獻人數/格子數夠不夠、成本、濫用跡象。

## 9. Phase 1 定案（私人小圈）
| 項目 | 決定 |
|---|---|
| 群組定位 | **私人小圈**：邀請碼組一隊，只跟隊友共享（k-匿名門檻可小） |
| 來源呈現 | **混合**：自己的上車點加重、隊友的當背景一起排名 |
| 回填歷史 | **要**：手機端先把同格子合併（只算不重複的格子）、分批寫、單次上限 500 格 |
| k-匿名 N | **2**（至少兩筆才顯示；濾單筆雜訊、也不洩漏單一個人） |
| 附近半徑 | **2–3km** |
| 近期加權 | 近 30 天 ×1、更舊 ×0.5 |
| 貢獻上限 | **每人每日 300 次**（日常用不到，只擋 bug/濫用）；**回填一次上限 500 格** |

> 成本觀念：Firebase 免費額度＝**整個專案**一天 2 萬次寫入（大家共用，非每人）。私人小圈（≤10 人）日常
> 一天約數百次寫入，用不到 2%；唯一要節流的是「回填」→ 先合併＋分批＋上限即安全。
