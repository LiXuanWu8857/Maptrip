# Maptrip 模組化 — 邏輯與做法

**現況：v1.1.428**。給下一個 session 的工程方法文件：這支專案「更新一律走模組化」是**使用者指定的核心規則**，
這份把「為什麼這樣做、要遵守哪些規則、怎麼把 app.js 的東西抽成模組、怎麼測、怎麼部署、並行開發怎麼不打架」寫清楚。

> 權威來源仍是 `CLAUDE.md` 的「慣例」段；本文件是它的展開＋實作範本。模組清單以 `ls js/` 與 `CLAUDE.md` 為準。

---

## 0. 一句話

**app.js 不要再長肥。新功能開一支 `js/xxx.js` 做成 `window.MaptripXxx`；改舊功能去它已經抽出來的那支模組改；
抽模組時逐字搬、app.js 留同名薄包裝轉呼叫、呼叫端零改動；每塊都配 Playwright 測試，零 pageerror 才算完成。**

---

## 1. 為什麼要模組化（動機）

- **app.js 曾經 3900+ 行**，單檔巨大 → 難讀、難改、容易踩到不相干的東西。
- **多個 session 並行開發**：大家都改同一個 app.js＝天天撞 merge 衝突。拆成多支小檔，各改各的，衝突大減。
- **可測試**：把邏輯抽成**純函式**，才能用 node/Playwright 針對它寫回歸測試（不用整個 App 跑起來）。
- **token 成本**：改一個小功能不必把 3900 行 app.js 讀進來。

成果：app.js 3909 → **2525 行**；已抽出 **38 支** `js/*.js` 模組。

---

## 2. 三條核心規則（使用者指定，必守）

1. **新增功能** → 開一個新的 `window.MaptripXxx` 模組（`js/xxx.js`），**不要**把新邏輯堆回 app.js。
2. **修改舊功能** → 先找到它**已經抽出來的那支檔案**（見 `CLAUDE.md`「已抽」清單或 `ls js/`），**在那支模組裡改**；
   **不要**去改 app.js 的薄包裝（薄包裝只負責轉呼叫）。若該功能**還沒模組化** → 先「抽成模組」再改。
3. **改完一定測** → 跑對應的 Playwright 測試（模組回歸＋瀏覽器接線/行為），**零 pageerror** 才算完成，再部署。

---

## 3. 一個模組長什麼樣（結構）

零 build、零打包。每支就是一個 IIFE 把命名空間掛到 `window`：

```js
// js/xxx.js
window.MaptripXxx = (function (global) {
  'use strict';

  // ── 私有狀態 ──
  var _state = null;

  // ── 純函式（不碰 DOM/全域，吃參數回結果 → 最好測）──
  function _compute(a, b) { return a + b; }

  // ── 會碰 DOM / 全域的動作 ──
  function doThing(id) { /* ... */ }

  // ── 對外介面（動作 + 給測試的純函式都 export）──
  return {
    doThing: doThing,
    _compute: _compute        // 底線開頭＝內部/測試用，仍 export 方便 node 測
  };
})(typeof window !== 'undefined' ? window : globalThis);
```

三個要點：
- **命名空間** `window.MaptripXxx`（大駝峰）。
- **純函式盡量多**（`_xxx`），因為純函式最好測；會碰 DOM 的動作越薄越好。
- **結尾 `(window||globalThis)`**：讓 node 測試能 `globalThis.window = globalThis; require('js/xxx.js')` 直接拿到模組。

### 依賴注入（模組需要 map / 共用活狀態時）

有些模組要用到地圖物件或 app.js 的共用狀態（activeTrip 等）。**不要**在模組裡 `import`，而是 app.js 在 boot 時
把它們**注入**進去（傳 getter/setter）。例：`recorder.js` 的 `init(ctx)` 收 `ctx.getActive/setActive/getMap…`；
`replay.js` 是第一個用依賴注入的。這樣模組不直接依賴 app.js 內部變數，仍可獨立測（測試時注入假的）。

---

## 4. 怎麼把 app.js 的東西抽成模組（SOP，血淚重點）

> 核心原則：**逐字搬，不是重寫。** 抽出來的邏輯要跟原本 app.js **一字不差**，否則容易悄悄改掉行為。

1. **逐字搬**：把 app.js 那段函式**原封不動**剪到 `js/xxx.js`，包進 `window.MaptripXxx`。
   不是寫個「骨架」或「我理解的版本」——是**原文搬過去**。
2. **app.js 留同名薄包裝**，只負責轉呼叫 → **呼叫端（HTML onclick、其他函式）完全不用改**：
   ```js
   // app.js（薄包裝，真實範例）
   function startTrip() { return MaptripRecorder.startTrip(); }
   function startGpsWatch() { return MaptripRecorder.startGpsWatch(); }
   ```
3. **載入順序**：`index.html` 用 `<script>` 依序載入，**被依賴的先載**（util → 用到 util 的模組 → app.js 最後）。
4. **GPS/熱路徑刻意留 app.js**：像 `onGpsUpdate` 逐點收錄這種每秒跑的熱路徑，**故意不抽**（抽了反而加一層呼叫成本、風險高）。
5. **配兩種測試**（見 §5）：
   - **回歸測試**：模組輸出 vs 原版 app.js 邏輯**逐字相同**。
   - **接線測試**：在瀏覽器裡 enable → 實際行為正確、零 pageerror。

## 5. 測試慣例（改完一定跑）

### 兩類測試
- **純函式回歸**：node 直接 `require` 模組，對 `_xxx` 丟輸入驗輸出（快、穩）。
- **瀏覽器接線（Playwright）**：用真實 `css/style.css` + 真實模組渲染/操作，量 DOM、驗行為、**監聽 `pageerror` 必須為 0**。

### 沙箱指令（容器重啟測試會消失、需重建）
```bash
# 純函式 / _cardHtml 這種回字串的：node 直接測
env -u HTTPS_PROXY -u HTTP_PROXY -u https_proxy -u http_proxy \
  NODE_PATH=/opt/node22/lib/node_modules /opt/node22/bin/node 測試.js

# 視覺/接線：Playwright（Chromium 固定路徑）
# chromium: /opt/pw-browsers/chromium-1194/chrome-linux/chrome
# 本機站：python3 -m http.server 8123 --directory /home/user/Maptrip
```

### node 測純函式的起手式
```js
globalThis.window = globalThis;           // 模組掛在 window
require('/home/user/Maptrip/js/xxx.js');
const X = globalThis.MaptripXxx;
// 對 X._compute(...) 等純函式做斷言；最後印 ALL PASS / FAILED
```

### 會碰 DOM 的純函式要防呆
node 沒有 `document`。模組裡若純函式會間接碰 DOM，要加 `if (typeof document === 'undefined') return …`，
否則 node 測試一 require 就炸（例：`booking.js _isRecording` 就加了這道）。

### 可測性設計：把「決策」抽成純函式
會碰 DOM/全域的動作裡，把**判斷邏輯**抽成一個吃參數的純函式再 export，就能在 node 測它，不用起整個 App。
真實例：`booking.js _pickActiveId(list, recording, boundId, runningStart, now)`（判斷哪筆預約在跑車中）、
`sync.js _mergeBk(cloud, bak)`（換帳號預約備份合併）、`finance.js monthReport(...)`（月報算錢單一來源）。

## 6. 慣例細節 / 血淚坑

- **零 build**：沒有 webpack/bundler。`<script>` 直接載、靠載入順序。改 code 不用編譯，push 到 gh-pages 就生效。
- **薄包裝只轉呼叫**：改邏輯去模組改，別改薄包裝；薄包裝改了＝兩邊不一致。
- **CSS 命名撞名（v419 血淚）**：記帳者和預約都用 `.bk-` 前綴 → 記帳者動態注入的全域樣式漏到預約卡。
  解法：記帳者樣式用 `_scopeCss` 侷限在 `#bk-sheet/#bk-home` 容器內。**新模組取 class 名避免和別人撞；
  非用不可時要 scope 住。**
- **單一來源**：同一件事只算一次。例：算錢只有 `finance.monthReport`，記帳者報表和收支報表都走它、不各寫一份。
- **localStorage key 命名**：帶模組前綴（`maptrip_xxx` / `mt_xxx`），換帳號要清的在 `account-switch`/`sync` 的清除流程裡一起清。

## 7. 部署 + 並行開發（push 前必讀）

### 部署流程（每次完整走完）
1. 升版號 **4 個地方**：`js/app.js` APP_VERSION、`index.html` INDEX_VERSION、`version.json`、`sw.js`（註解＋`VER`）。
2. commit，push 到 `claude/mobile-website-version-Sl6cq`、`claude/module-refactor-token-optimize-nhj6kf`。
3. **同一 commit 也 push 到 `gh-pages`**（`git push origin HEAD:gh-pages`）——gh-pages 才是 App 實際載入的站。
4. **驗證 Pages deploy conclusion=success**。
5. 使用者更新：完全關 App、再開兩次（SW：第一次安裝、第二次生效）。

### 並行開發（多 session，血淚規則）
1. **動工前先 `git fetch`** 對齊 gh-pages 最新，別在舊基礎上做。
2. push 被拒（non-fast-forward）＝有人先推了 → **rebase/cherry-pick 到對方之上，絕不覆蓋對方成果**。
3. **先看對方改了什麼**（`git diff`），衝突處**兩邊功能都保留**（例：exports 那行兩邊各加各的，合併成一行都留）。
4. 版本號取「對方最新 ＋1」。
- commit 訊息：**英文標題＋繁中內文**（說明根因與修法），結尾附 Playwright 驗證結果。

## 9. 新增一個模組：Step-by-step 範本

以「加一個新功能 Foo」為例：

1. **開檔** `js/foo.js`：
   ```js
   window.MaptripFoo = (function (global) {
     'use strict';
     function _calc(x) { return x * 2; }          // 純函式，好測
     function run() { /* 碰 DOM 的動作 */ }
     return { run: run, _calc: _calc };
   })(typeof window !== 'undefined' ? window : globalThis);
   ```
2. **index.html 載入**（被依賴者先載；放對順序）：
   ```html
   <script>document.write('<scr'+'ipt src="js/foo.js?v='+window.INDEX_VERSION+'"></scr'+'ipt>');</script>
   ```
3. **app.js 接線**：選單/按鈕 onclick 呼叫 `MaptripFoo.run()`；若要共用 app.js 狀態就 `MaptripFoo.init({ ... })` 注入。
4. **寫測試** `foo.js`（scratchpad）：
   - 純函式：`require` 後驗 `MaptripFoo._calc(3)===6`。
   - 接線：Playwright 載真實 css + 模組，點按鈕→驗 DOM，`page.on('pageerror')` 計數＝0。
5. **跑測試**（§5 指令），零 pageerror。
6. **升版號 4 處 → commit（英標＋繁中內文＋驗證結果）→ push Sl6cq/nhj6kf/gh-pages → 驗證 Pages success。**
7. 回報使用者：先結論、白話根因、要他做什麼（關 App 開兩次）。

---

## 10. 修改舊功能：Step-by-step

1. `git fetch` 對齊最新。
2. 在 **已抽出的那支模組**裡改（不是 app.js 薄包裝）。還沒抽？先抽（§4）再改。
3. 若行為由純函式決定 → 直接改純函式＋補測試最省事。
4. 跑回歸＋接線測試，零 pageerror。
5. 升版、部署（§7）。
